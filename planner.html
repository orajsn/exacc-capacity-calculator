Before resizing: requirements and memory formula

A lower estimate does not guarantee OCI will allow the change. Check ACD CPU allocations and reservations, used storage, and the console minimums. Changing ECPUs per VM or maximum ACDs triggers rolling restarts. Check the maintenance impact before changing memory per CPU. Oracle scaling guidance.

Current memory rule: (ECPUs per VM × GB per ECPU + 40 + 0.3 × ECPUs per VM) × 1.02 × VM count. Applies to AVMCs created after 29 September 2026 and existing AVMCs after memory per CPU changes. Confirmed legacy AVMCs omit the 0.3 term. Planning uses decimal 300 MB = 0.3 GB and budgets at least 135 GB per VM for the current rule; check the console for rounding differences.
Which changes free capacity?
  • ADB autoscaling: borrows idle CPU within its parent ACD. It does not resize the AVMC allocation. Autoscaling reservations can constrain later AVMC scale-down. Compute management.
  • Lowering ADB ECPUs: is not an AVMC memory resize. Released CPU can remain reclaimable in the ACD until its restart; check reservations before shrinking the AVMC.
  • Lowering AVMC ECPUs or GB/ECPU: changes the infrastructure memory allocation. Changing a legacy memory ratio switches to the new formula, so check the resulting total.
  • Deleting ACDs: does not by itself reduce configured maximum ACD slots. Lowering that maximum reduces the estimated local allocation by 51.5 GB per slot per VM. The console still sets the lowest allowed value.
  • Restart impact: changes to ECPUs/VM or maximum ACDs cause rolling AVMC, ACD and ADB restarts. Application continuity depends on connection/replay configuration and workload testing; do not assume zero interruption. Scaling procedure.

Use this calculator to compare resource changes. Oracle Support or the account team must confirm a customer-specific recommendation and maintenance plan.

Formulas, assumptions and sources

How the calculation works

For each AVMC, N is its configured maximum ACD count and V is its selected DB-server count.

Local GB = [ image + (100 + 50 × N) × 1.03 + 2 ] × V

For two X11M nodes: 578 GB per AVMC + 103 GB per reserved ACD slot. Each ACD is counted once, even though its storage is allocated on every selected node. An AVMC can have at most 16 ACDs.

Assumptions, source differences and scope
  • The result is a reservation estimate, not measured disk usage. Check capacity on every selected server.
  • Oracle’s detailed formula gives 681 GB for one ACD on two X11M nodes; its worked example shows 682 GB. Other summary examples also differ. This calculator consistently uses the detailed formula and shows decimal GB. Confirm final reservations in the console.
  • All buffers are user-selected: local storage starts at 10%; CPU, memory and manually entered Exadata storage start at 30%. These are planning assumptions, not Oracle-mandated margins.
  • Memory uses the current or confirmed legacy rule per AVMC. Old scenarios without a rule are unconfirmed and use the conservative current estimate; saved reference totals stay unchanged. ACD creation additionally requires available CPU per node.
  • Local GB belongs to database servers. Shared Exadata storage is separate; the optional TB check uses manually entered console capacity and total allocations. It does not derive internal overheads or backup reservations.
  • Custom and mixed-service deployments require console confirmation of VM limits. Current X11M Autonomous presets use Oracle’s documented 6 VMs/server, or 2 for Base.
  • Conventional VMC filesystem and VM-backup calculations will use a separate model. For now, include their console-reported local allocations as “Other local GB”. Exascale support in the conventional service does not establish Autonomous support.

Saving and backup On this device or in a file

Saved plans stores separate customer projects in this browser when you choose Save on this device. Customer data is not sent to GitHub, OCI or a server. Owner aliases and Plan IDs are labels, not logins or access controls.

  1. Click Download backup. Your browser downloads the current plan with its customer, project and Plan ID, usually to Downloads or the folder you choose.
  2. Keep that JSON file. It contains all machines, entered allocations, planning settings and recorded Before values. Apply any preview you want to keep before saving.
  3. Next time, click Open plan file and select the file to resume editing.

JSON is the editable configuration; Print / PDF is only a report. Closing or refreshing can lose edits that are not in your downloaded file. Your browser may warn, but do not rely on that warning as a backup.

Each saved plan has its own copy. Saving on this device turns on automatic updates for that plan. Other browsers or devices need its JSON file; the Plan ID alone cannot retrieve it elsewhere.
